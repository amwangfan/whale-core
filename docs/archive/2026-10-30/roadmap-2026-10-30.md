**用途：** 转交给负责 `whale-core` 仓库的
AI，作为架构决策、实现规划和验收依据。\
**版本：** 2026-10-30\
**核心仓库：** https://github.com/amwangfan/whale-core\
**相关仓库：** https://github.com/amwangfan/whale-io

> 这份文档是技术方向与任务约定，不代表所有列出的功能已经实现。开始改代码前，必须重新检查当前
> `main`、目录、测试和最近提交，以仓库现状为准。不要仅根据本文件推断某项功能仍缺失，也不要在未核对代码的情况下重复实现。

## 1. 项目目标

`whale-core`
是鲸鱼（Whale）的核心大脑与可复用运行时，不是某一个聊天机器人，也不是仅为某个眼镜型号服务的适配器。

长期目标：

1.  **核心大脑独立：**
    负责理解输入、管理上下文与记忆、判断意图、规划任务、选择能力、协调执行，并根据结果继续处理。
2.  **多入口、多出口：**
    手机、雷鸟眼镜、VoIP、QQ、网页控制台及未来的桌面/其他渠道，都是核心的入口或出口，不应各自再造一套大脑。
3.  **插件可插拔：**
    模型、记忆、语音、搜索、媒体生成、Shell、渠道等可单独启用、禁用、替换和配置。
4.  **同仓库可体验：**
    官方插件、示例、配置档和文档尽量放在同一个仓库，用户下载后可以快速启动基础版本，再按需启用高级能力。
5.  **可自定义：**
    用户可替换模型服务、记忆后端、语音服务和插件；不需要为常见自定义操作修改核心代码。
6.  **可视化管理：**
    提供网页控制台，用于查看运行状态、管理配置和插件、查看记忆/任务/日志、处理审批与诊断。
7.  **可部署、可打包：**
    同一套核心既能在云端服务器运行，也能在个人电脑运行；未来可封装为桌面应用，不因打包需求而重写核心。
8.  **安全、可诊断、可恢复：**
    能解释某个动作为什么发生、使用了什么能力、是否经过授权、执行结果是什么；记忆可备份、导出和删除。

设计原则：核心保持小而稳定；具体能力放在提供者/插件中；跨插件的组合流程放在
Skill/工作流中；前端只调用受鉴权的
API；真实动作由基础设施执行并接受核心策略门控。

## 2. 技术决策：继续使用 Python，不整体迁移到 Node.js

### 2.1 决策

**当前阶段保留 Python 作为核心运行时。**
不因为要做网页控制台或桌面应用，就将整个 `whale-core` 改写成
Node.js/TypeScript。

理由：

-   当前仓库已经有 Python
    核心、记忆、意图/行动、插件契约和安全策略。重写会产生大量迁移成本，并延迟真正需要的功能。
-   Python 适合模型编排、数据处理、检索、语音/多模态 SDK 和 AI
    生态集成。
-   Node.js
    并不会自动让模型调用更聪明、更低延迟或更容易打包；真实延迟通常由模型、网络、音频链路和任务编排决定。
-   Web 前端本来就适合 TypeScript。前端采用 TypeScript
    不要求后端也必须使用 Node.js。
-   Python 可以通过稳定的 HTTP/WebSocket API、进程间协议或 MCP
    与其他语言的插件协作。

### 2.3 为什么不现在整体迁移 Node.js

只有当某个独立子系统确实存在明确的 Node.js 优势时，才考虑使用
Node.js，例如某些已有 Node SDK
的渠道适配器、浏览器自动化适配器或前端开发工具。它们可以作为独立进程，通过
HTTP、WebSocket、stdio/MCP 或明确的 RPC 协议与 Python 核心连接。

不要仅为"统一语言"而重写核心。若未来确实要迁移某个模块，必须先定义与语言无关的协议、测量收益并分阶段迁移；禁止一次性推翻现有实现。

### 2.4 打包策略分阶段进行

1.  **开发阶段：** `uv sync` / `uv run`，提供 CLI。
2.  **普通用户试用阶段：** 一键
    setup、诊断命令、可选依赖组、清楚的配置向导。
3.  **云端阶段：** Docker Compose
    或标准服务部署；数据和密钥保存在持久化目录/环境变量/密钥管理中。
4.  **桌面阶段：** 核心和网页控制台稳定后，再做 Tauri 安装包；Python
    核心可以被打包成 sidecar。
5.  **不要一开始追求单个巨大安装包。** 视频生成、语音、GPU
    模型和各供应商 SDK
    的体积与系统依赖差异很大。基础包应小，高级能力按需安装。
6.  打包方案必须覆盖版本升级、配置迁移、日志位置、进程退出、端口冲突、数据备份/恢复和卸载行为。卸载软件不应默认删除用户记忆和数据。

## 3. 总体架构

建议在现有实现上逐步形成以下逻辑结构，不要求一次性移动所有文件。

``` text
输入端（网页 / 手机 / 眼镜 / VoIP / QQ / 定时事件）
                    |
                    v
             Channel / Input Adapters
                    |
                    v
             Whale Runtime / API
       +------------+-------------+
       |            |             |
   对话编排      事件/感知流程    任务/工作流
       |            |             |
       +------------+-------------+
                    |
        Context / Persona / Memory
                    |
           Model & Capability Router
                    |
              Plugin Gateway
                    |
      +-------------+------------------+
      |             |          |       |
   搜索/浏览      ASR/TTS    生图/视频  Shell/其他工具
      |             |          |       |
      +-------------+----------+-------+
                    |
       Policy / Approval / Audit / Quota
                    |
            外部服务与执行基础设施
```

### 3.1 对话流程与事件流程并存

不要把所有功能塞进一个巨大 Agent 类。建议：

-   保留现有 `WhaleAgent`
    的感知---决策---行动思路，用于外部事件、主动行为和行动闭环。
-   新增或完善统一的 `WhaleRuntime` /
    `ConversationOrchestrator`，负责普通聊天、上下文组装、模型调用、工具循环、结果整合和会话状态。
-   两条流程共用记忆、人格、模型/能力注册表、权限策略、审计和回执机制，但保留各自的调度与失败处理。
-   模型可以提出意图或工具调用，但不能自行授予权限、跳过审批或决定自己的风险等级。

### 3.2 核心不变量

以下内容不能被普通插件随意替换或绕过：

-   所有者/渠道身份验证与授权；
-   工具与 Shell 的权限策略；
-   高风险动作的审批机制；
-   主动行为频控、暂停开关和审计；
-   密钥保护、记忆隔离和删除语义；
-   超时、输出大小限制、任务取消和幂等处理。

插件可以提供能力，不能自行修改核心安全不变量。

## 4. 插件系统：保留现有分类，补齐管理能力

### 4.1 现有六类插件分类继续保留

沿用现有 `PluginKind`：

-   `input`：输入事件，例如日程、天气、应用状态、语音输入。
-   `output`：执行输出动作，例如通知、邮件、生成结果推送。
-   `channel`：双向渠道，例如 QQ、手机、VoIP、眼镜。
-   `processor`：内部处理、任务委托、摘要、记忆整理等。
-   `model`：模型/能力提供者。
-   `memory`：记忆存储、召回、同步、备份等后端。

不要为了每一种功能再新增一个
PluginKind。**插件类型是实现类别，Capability
才是可被核心选择和调用的功能契约。**

### 4.2 新增统一 Capability 契约

建议为每个能力定义稳定的 ID、版本、输入/输出
Schema、错误格式、超时和流式能力。例如：

  能力 ID                                           职责
  ------------------------------------------------- ------------------------------
  `llm.chat`                                        生成文字回答，支持多轮上下文
  `llm.intent`                                      产出结构化意图计划
  `llm.tool_executor`                               在限定工具集和轮数内执行任务
  `memory.store` / `memory.recall`                  记忆写入与召回
  `embedding.embed`                                 文本向量化
  `asr.transcribe` / `asr.stream`                   普通与流式语音识别
  `tts.synthesize` / `tts.stream`                   普通与流式语音合成
  `voice.realtime`                                  原生实时语音输入/输出
  `media.image.generate`                            图片生成
  `media.video.generate`                            异步视频生成任务
  `web.search` / `web.fetch`                        搜索网页与抓取/读取网页
  `shell.execute`                                   受控命令执行
  `channel.qq` / `channel.glass` / `channel.voip`   渠道能力

同一个供应商插件可以提供多种能力；多个不同插件也可以提供同一种能力。核心根据配置、能力、可用性、延迟、成本和用户偏好选择
provider，避免把供应商型号硬编码进业务逻辑。

### 4.3 Capability 与 Tool、Skill 的区别

-   **Capability：** 系统能够做什么，例如 `web.search`。
-   **Tool：** 模型可以按 Schema 调用的具体操作，例如
    `search_web(query, limit)`。
-   **Skill：**
    说明如何组合工具完成一个目标的可复用工作流，例如"搜索多个来源、核实信息、整理摘要、给出引用"。

不要把每一个 Skill 都写成新的 Python
插件。能用现有工具组合完成的流程，优先用 Markdown
或结构化工作流描述。只有需要新的执行逻辑或外部 API 时，才新增插件。

### 4.4 插件清单与生命周期

在现有 `PluginManifest` 上增加或映射以下元数据。具体格式可用
JSON/TOML，但必须有 Schema 和版本：

-   `id`、`version`、`api_version`；
-   `kind`、`provides`；
-   `entrypoint` 或外部进程启动方式；
-   `config_schema`；
-   `permissions`；
-   `dependencies` / 可选依赖组；
-   `healthcheck`；
-   超时、输出大小限制和兼容性信息。

生命周期建议：发现 → 校验 → 配置 → 初始化 → 健康检查 → 启用 → 停止/禁用
→ 卸载。

约定：

1.  官方插件放在同一个仓库中，具有独立目录、测试和依赖声明。
2.  插件应可单独启用/禁用；未启用插件不能在后台悄悄运行。
3.  插件升级不得静默覆盖用户配置；卸载插件不得顺带删除用户记忆。
4.  不要仅靠扫描目录并任意 `import`
    来发现第三方代码。注册必须显式且可审计。
5.  Python entry points
    可用于发现已安装插件，但"可发现"不等于"可信"。第三方插件安装/启用必须明确告知其权限。
6.  可信官方插件可以在核心进程内运行；第三方或不可信插件优先采用独立进程/受控
    RPC/MCP/HTTP，避免直接取得核心进程的全部权限。
7.  插件失败应能隔离并回报健康状态，不应导致核心主循环崩溃。
8.  对 API Key、Cookie、账号登录态等敏感配置做遮蔽显示，不写入
    Git，不写入普通日志。
9.  插件必须声明 API 版本并有兼容性检查。

参考 OpenClaw 的插件架构与 Skills
区分：https://github.com/openclaw/openclaw/blob/main/docs/plugins/architecture.md

## 5. 网页端可视化控制台

这是项目的正式需求，不是可有可无的后期装饰。建议先做
MVP，再扩展为完整控制台。

### 5.1 技术方案

-   前端：TypeScript + React + Vite。
-   后端：在 Python 核心旁提供 API 服务；优先评估 FastAPI/ASGI。
-   普通请求用 REST；实时运行状态、任务进度、日志事件使用 WebSocket 或
    SSE。
-   前端只访问 API，不直接操作 SQLite 文件、服务器文件系统或密钥。
-   开发模式允许 Vite 独立热更新；生产模式可以由 API
    服务提供构建后的静态文件，或作为独立静态前端部署。
-   网页控制台与核心分离部署，但保持同仓库版本化。

### 5.2 MVP 页面

1.  **总览 Dashboard**
    -   核心运行状态、版本、运行时长；
    -   已启用插件、模型/provider 健康状态；
    -   最近任务、错误、资源/成本摘要；
    -   快速启动 `doctor` 或测试连接。
2.  **首次设置 Setup**
    -   选择 `demo`、`cloud`、`local` 配置档；
    -   选择模型 provider、填写 API Key、测试连接；
    -   选择默认记忆后端；
    -   展示哪些能力可用、哪些依赖尚未安装。
3.  **模型与能力 Providers**
    -   查看某能力当前 provider；
    -   更换模型、设置超时/回退策略；
    -   测试连接、查看错误和延迟；
    -   Secret 输入只显示已配置/未配置或脱敏状态，不能回传明文密钥。
4.  **插件管理**
    -   插件列表、版本、来源、能力、状态、健康检查；
    -   启用、禁用、配置、测试、更新；
    -   权限清单和风险提示；
    -   显示缺少的依赖、凭据和系统工具。
5.  **对话与记忆**
    -   查看会话与摘要；
    -   搜索记忆、查看来源/证据/时间；
    -   删除单条记忆、导出记忆、查看人格配置；
    -   记忆写入、提炼、召回均应可追踪。
6.  **任务与行动**
    -   查看当前任务、状态、步骤和结果；
    -   查看模型提出的 Tool Call 与实际执行结果；
    -   对需要审批的操作进行批准/拒绝；
    -   取消任务、查看超时和失败原因；
    -   能明确区分"模型提出动作"和"动作已经实际执行"。
7.  **日志与诊断**
    -   插件日志、API 错误、任务失败和健康检查；
    -   过滤敏感信息；
    -   提供复制诊断摘要的能力；
    -   不在日志中默认记录私人对话原文、音频字节或 API Key。
8.  **设置与安全**
    -   认证、允许的来源、静默时段、主动行为预算；
    -   Shell 权限档位、审批策略、暂停开关；
    -   备份状态、导出/恢复操作；
    -   配置修改应有校验、错误提示和必要的审计记录。

### 5.3 建议 API 轮廓

具体路由可以按现有代码调整，但必须先定义 API Schema 和版本。示例：

``` text
GET    /api/v1/status
GET    /api/v1/health
GET    /api/v1/providers
POST   /api/v1/providers/{id}/test
GET    /api/v1/plugins
POST   /api/v1/plugins/{id}/enable
POST   /api/v1/plugins/{id}/disable
GET    /api/v1/plugins/{id}/health
GET    /api/v1/memory/search?q=...
GET    /api/v1/memory/{id}
DELETE /api/v1/memory/{id}
POST   /api/v1/memory/export
GET    /api/v1/tasks
GET    /api/v1/tasks/{id}
POST   /api/v1/tasks/{id}/cancel
GET    /api/v1/approvals
POST   /api/v1/approvals/{id}/decision
GET    /api/v1/events              # 或 WebSocket/SSE 端点
```

以上是建议，不是已存在的 API。实现前应统一错误格式、分页、鉴权、幂等性和
API 版本策略。不能通过一个泛化的"执行任意命令"API
让网页绕过已有的策略层。

### 5.4 网页安全要求

-   默认只监听 `127.0.0.1`，云端部署必须显式配置监听地址、鉴权和 HTTPS
    反向代理。
-   不能把管理 API 无鉴权地暴露到公网。
-   设置明确的 CORS 来源；需要 Cookie 会话时防范 CSRF；WebSocket/SSE
    连接同样要鉴权。
-   API Key 不能回显；优先用环境变量、系统密钥环或专门的 Secret Store。
-   `web.fetch` 要防
    SSRF：限制本机/内网/云元数据地址、校验重定向目标，并限制响应大小和超时。
-   网页输入不能直接变成 Shell 命令。Shell
    必须经过身份验证、策略裁决、必要的审批、受控执行器和审计。
-   对插件启停、权限变更、备份恢复、删除记忆等重要动作记录审计事件。
-   不可信网页内容、检索结果、记忆内容和插件输出都应被视为数据，而不是可信系统指令。

## 6. 意图模型与统一运行时

### 6.1 意图计划结构

新增或完善结构化的 `IntentPlan`（名称可按现有契约调整），至少包含：

-   `intent_id`、`goal`、`kind`；
-   必要的槽位/参数和缺失信息；
-   需要的 Capability/Tool；
-   预期输出与成功条件；
-   需要澄清还是可以执行；
-   `reason`、证据/上下文引用；
-   任务 ID、超时和取消语义。

注意：模型输出的 `risk`
只能作为参考，真正的权限和风险级别必须由核心根据工具清单、策略和执行上下文计算。模型不能通过输出
`approved=true` 自行批准动作。

### 6.2 任务执行闭环

建议标准流程：

1.  接收输入并验证来源、身份与渠道；
2.  组装系统规则、人格、会话历史和相关记忆；
3.  先用规则处理确定性、低成本场景；必要时才调用意图模型；
4.  校验结构化意图和参数；
5.  选择能力 provider；
6.  通过策略层检查权限、风险、额度和审批；
7.  执行工具，限制轮数、超时、输出大小和资源；
8.  记录执行回执与必要的审计元数据；
9.  把摘要/结果返回对话模型或渠道；
10. 根据可信证据决定是否写入长期记忆；
11. 返回用户可理解的结果，不得把"已计划"伪装成"已执行"。

聊天、主动行为和复杂任务可以共享这一闭环，但应有独立的预算、超时和优先级，避免长任务阻塞实时语音。

### 6.3 上下文隔离

-   陪伴/对话模型不应被大量 Shell 原始输出或网页全文挤占上下文。
-   工具执行器可以处理长输出，但返回核心的内容应是摘要、关键证据、必要引用和回执。
-   不可信外部内容必须与系统规则分层；网页、文件、记忆里的命令不自动变成执行指令。
-   模型切换时应保留人格与工具契约，不应因更换供应商而改变权限边界。

## 7. 记忆系统

### 7.1 保留现有记忆基础

保留当前 `MemoryStore`、SQLite
持久化、情节/偏好/人格连续性记忆及现有的证据化记忆整理机制。在其上完善，而不是另起一套并行记忆系统。

### 7.2 记忆类型与行为

至少区分：

-   **会话上下文：** 当前会话多轮历史，按上下文预算截断/摘要。
-   **情节记忆（episode）：** 发生过的对话、事件和任务结果。
-   **偏好/事实记忆（preference/fact）：**
    稳定偏好和用户明确确认的事实，带证据来源。
-   **人格连续性（persona continuity）：**
    名称、语气、称呼、表达规则、跨会话状态。
-   **工作记忆：** 当前任务进度、待办步骤、临时信息和任务状态。

对每条长期记忆记录来源、时间、类型、置信度或确认状态、关联证据及删除状态。不能把模型猜测的事实直接写成已确认事实。

### 7.3 召回与向量检索

-   先修好会话历史传递、SQLite 持久化、关键词召回、证据过滤、导出/删除。
-   向量 embedding、reranker、混合召回作为可选
    provider，不应成为启动核心的硬依赖。
-   第一版可以关键词召回；后续采用关键词 + 向量的混合召回和重排。
-   实时电话链路不应等待长时间的语义召回。
-   删除操作应影响真实持久化记录、索引和可控的派生缓存；必要时采用
    tombstone，不能只从界面隐藏。
-   保留 JSONL 导入/导出与备份恢复能力；定期进行恢复演练。
-   当前单机阶段优先采用一个 canonical SQLite
    数据库和单写者模型，不要让手机、网页和多个进程直接并发修改多个互相独立的数据库副本。

### 7.4 需要重新核查的现有问题

此前代码检查观察到以下风险点，实施前必须在当前 `main` 重新验证：

-   `WhaleCompanion.chat()` 是否把完整的会话历史传给
    `DeepSeekCompanion.reply()`；若没有，应补齐并加多轮测试。
-   `StubModelRouter` 是否仍只返回空的
    `Decision`；若是，明确它是测试替身，并实现真实路由或清楚的未配置错误。
-   插件注册机制是否仍仅靠宿主代码显式调用
    `register()`；若是，增加受控的清单加载与管理生命周期。
-   `ShellPolicy`
    只做裁决而不执行命令；真实执行器是否已经实现并具备系统级隔离，需要单独验收。
-   `MemoryStore` 的内存实现和 SQLite
    实现是否有一致的行为、测试和配置入口。
-   README、人格禁忌、系统提示与代码策略是否一致，避免文档说可以配置、代码却硬编码相反规则。

这些是待验证的代码审查线索，不应未经复查就当作当前缺陷结论。

## 8. 功能清单与优先级

### P0：先建立稳定、可体验的基础

目标：新用户能安装并运行基础版本；开发者能添加插件；核心能够多轮对话、记忆、判断意图并执行一个真实工具闭环。

1.  **运行时：** 统一对话编排、事件流程、模型路由、上下文和执行回执。

4.  **记忆 V1：** 多轮历史、SQLite

5.  **模型 provider：**
    至少一个实际文本模型提供者，并保留通用兼容接口；支持超时、错误处理和配置切换。
6.  **搜索工具：** `web.search` +
    `web.fetch`，能核查多个来源并在回答中保留来源链接。
7.  **CLI：** `setup`、`doctor`、`run`、`plugins list/enable/disable`
    等统一入口。
8.  **网页控制台 MVP：**

9.  **开箱即用配置：** `demo`、`cloud`、`local` 三个配置档；离线 demo
    使用 mock provider，不要求 API Key。
10. **基础安全：** 管理 API 鉴权、默认本地监听、Secret

11. **发布基础：**
    明确许可证、依赖与第三方素材清单、贡献说明和安装文档。

P0 的关键验收：一个全新环境可以依照 README 安装；离线 demo
可以启动；配置实际模型后能连续多轮对话；能写入并召回记忆；能调用搜索工具并引用结果；能在网页中查看状态和启停插件；未授权工具动作会被拒绝；CI
自动测试通过。

### P1：语音、媒体与受控执行

1.  **ASR：** `asr.transcribe`、可选
    `asr.stream`；供应商可换，支持超时和失败回退。
2.  **TTS：** `tts.synthesize`、可选 `tts.stream`；支持音色与语速配置。
3.  **实时语音：** `voice.realtime` 独立于普通文本链路，优先复用

4.  **Shell：** 受控执行器、工作目录白名单、非
    root、系统沙箱、超时强杀、输出限制、审计和审批；字符串黑名单不能作为唯一防线。
5.  **生图：** 统一
    `media.image.generate`，支持参数校验、任务状态和产物存储。
6.  **网页控制台增强：**
    记忆管理、任务列表、工具调用轨迹、审批队列、插件配置表单、健康检查。
7.  **混合记忆检索：** 可选 embedding、关键词融合、reranker。
8.  **配置/诊断：** provider 健康状态、错误分类、成本/额度统计。
9.  **外部渠道：** 将现有
    QQ、电话、眼镜能力逐步接入统一注册与审计体系，复用既有代码，不从零重写。

### P2：视频生成、主动生活和桌面打包

1.  **生视频：**
    异步任务提交、状态轮询/事件推送、取消/超时、失败回退、产物存储与过期清理。
2.  **自主探索/养鱼能力：**
    兴趣、探索窗口、来源核验、日记、候选分享、反馈调权和无回应退避。
3.  **主动行为：**
    跨渠道预算、静默时段、主题去重、暂停开关、审批/台账和用户反馈。
4.  **Skill 工作流：** 用已有工具组合搜索、阅读、总结、媒体生成与分享。
5.  **桌面应用：** 核心/API 稳定后用 Tauri 2 包装控制台并携带 Python
    sidecar。
6.  **更多 provider 与插件生态：**
    社区插件兼容性、版本迁移、可信来源和权限审查。
7.  **多设备/多用户：** 只有确实需要多宿主机或多 owner 时，再升级记忆
    REST API、租户隔离和同步协议。

### 重要依赖顺序

不要同时启动所有功能。推荐顺序：

`Runtime + IntentPlan + PluginManager + Memory V1` →
`实际 LLM + Web Search Tool + CLI` → `API + Web 控制台 MVP` →

## 10. 安全与可靠性底线

1.  **身份验证：** 外部渠道事件必须证明来源并完成显式 owner/channel
    绑定；不能仅凭昵称判断身份。
2.  **最小权限：**
    每个插件只拿完成工作所需的权限；第三方插件默认不可信。
3.  **Shell 隔离：** 执行器使用非 root
    专用账户和操作系统级隔离；限制文件系统、网络、CPU、内存、进程数和运行时间。不能仅依赖正则表达式过滤。
4.  **模型权限：**
    模型输出不是授权凭据；工具参数必须校验，风险由核心策略判定。
5.  **审批：**
    发消息、主动电话、交易、删除、文件写入和其他高风险动作应根据策略要求审批；授权范围应可见、可撤销。
6.  **主动行为：**
    提供全局暂停开关、额度、静默时段、幂等台账和反馈调节。
7.  **提示注入：**
    网页、视频字幕、记忆、附件和工具输出均视为不可信数据，不能覆盖系统规则或提升权限。
8.  **隐私：**
    默认不记录音频字节；私人转写文本不进入普通日志；Secret、Cookie
    和令牌不写入仓库/日志。
9.  **网络安全：** API 默认本地监听；云端部署须有鉴权和 TLS；限制
    SSRF、任意文件访问和不受控 URL 重定向。
10. **任务可靠性：** 工具执行必须有超时、取消、有限重试、幂等性和明确的
    `success/failed/unknown` 结果；不对状态未知的外部动作盲目重试。
11. **数据恢复：**
    支持记忆导出/备份；恢复后执行数据库完整性检查与冒烟测试。
12. **成本限制：**
    模型、搜索、语音和媒体生成均应可设置预算/额度；长任务不能无限循环。
13. **许可合规：** 确认 `whale-core` 自身的
    LICENSE；列出第三方插件、SDK、模型、人格卡和素材的许可证与使用限制。发布前必须解决根目录缺少明确许可证的问题（先检查当前仓库，避免误判）。

## 11. 测试与验收要求

每个功能必须包含测试，不以"代码能导入"作为完成标准。

### 核心测试

-   连续多轮对话确实携带历史；

-   记忆可持久化、召回、导出、删除；重启后行为一致；
-   记忆证据与来源能追踪；未确认推断不会被静默提升为确认事实；
-   插件禁用后不应继续提供能力；插件故障不应拖垮核心；
-   管理 API 的未授权请求被拒绝；
-   网页中 Secret 不会被回显；
-   Shell 沙箱和权限策略要有专门的负向测试；
-   demo 模式明确使用 mock，且不依赖外部 API；
-   CI 覆盖 lint/type checks（按项目适用）、pytest、前端构建和 API
    集成测试。

### 网页控制台验收

-   新安装后可打开网页并看到核心状态；
-   能配置 provider 并测试连接；
-   能查看插件能力、启停插件并发现缺少的依赖；
-   能看到任务状态、失败原因和工具调用结果；
-   记忆浏览、删除、导出操作与后端数据一致；
-   未授权用户不能执行管理动作；
-   关键操作有明确结果提示，不在请求未完成前显示成功。

### 发布验收

-   从干净环境按 README 操作可成功启动；
-   依赖安装、升级、卸载和恢复路径有文档；
-   没有真实密钥、Cookie 或个人数据进入 Git；
-   LICENSE 和第三方许可证清单明确；
-   版本号、插件 API 版本和迁移说明一致；
-   所有新增功能在文档中标注真实状态，不将
    stub/模拟接口称为已完成的真实功能。

## 12. 代码变更与协作约定

负责实现的 AI 应遵循以下工作方式：

1.  **先审查当前仓库。** 检查 `main`、最近
    commits、目录、测试和文档，确认哪些能力已经存在、哪些是

3.  **小步修改。**

4.  **先定义契约再接供应商。** 先写

5.  **不为统一语言而迁移。** Python 核心保留；网页采用

7.  **先测试再宣称完成。**

8.  **文档同步更新。** 修改 API/插件契约时更新文档、示例和兼容性说明。
9.  **不擅自执行外部破坏性动作。**
    不擅自部署、改生产环境、删除用户数据、推送危险命令或变更外部账号配置。
10. **PR/Issue 以具体问题为单位。** 每个 PR
    有目的、范围、测试和回滚方式；不要为了"整理"大规模改动无关文件。
11. **不要把设计建议冒充仓库现状。** 本文中的 CLI、API

## 16. 子智能体与并行协作：推荐操作

**对于复杂任务，使用子智能体/子代理进行并行研究、独立审查和专项实现是推荐做法，而不是禁用或仅在最后才考虑的选项。** 如果当前编程环境支持 subagents、task agents 或并行工作流，应积极使用；若不支持，则采用独立的并行分析任务、单独审查提示或分阶段角色检查来模拟这一工作方式。

### 16.1 适合拆分的工作

可以根据任务复杂度并行安排以下角色：

- **架构研究代理：** 检查当前架构、依赖边界和迁移路径；比较成熟开源项目与技术选型。
- **代码审查代理：** 独立阅读关键实现，寻找状态不一致、接口断层、异常路径和潜在回归。
- **测试代理：** 根据验收标准设计单元、集成、端到端和安全负向测试；检查测试是否真的验证目标行为。
- **前端代理：** 负责 React/TypeScript 控制台的页面结构、状态管理、API 客户端和前端测试。
- **后端/插件代理：** 负责 Python Runtime、Capability 契约、插件生命周期、provider 和 API 实现。
- **安全代理：** 专门检查认证、权限绕过、Shell 沙箱、SSRF、提示注入、Secret 泄漏和记忆删除语义。
- **文档与发布代理：** 检查 README、安装、配置迁移、插件开发文档、许可证和发行流程。
- **集成负责人/主代理：** 负责统一架构决策、分配边界、解决冲突、合并结果、运行全套测试，并对最终交付负责。

不要求每个任务都启动所有角色。应根据任务的风险和复杂度决定并行规模；对于涉及安全、架构或跨模块集成的任务，优先安排独立审查。

### 16.2 并行工作的边界

1. 主代理必须先定义接口、任务范围、文件所有权或可修改区域，避免多个代理同时修改同一核心文件。
2. 并行代理应得到明确的上下文、验收标准、不可变约束和交付格式；不能只给一句宽泛目标。
3. 对共享 API、数据模型、插件契约和数据库迁移，先由主代理统一设计，再让不同代理按契约实现。
4. 子代理的结论是候选结果，不是自动可信的最终事实。主代理必须审查差异、验证证据、解决不一致并运行集成测试。
5. 不允许把多个未经审查的代码补丁直接拼起来；必须检查冲突、重复实现、依赖版本、错误处理和风格一致性。
6. 对安全审查，应让审查者尽可能独立于实现者，避免只验证自己预设的设计。
7. 对代码生成或改动任务，明确代理是否可以直接写文件、是否可以提交，以及是否允许修改共享接口。未经授权，不得部署生产环境或执行破坏性外部操作。
8. 记录哪些部分由并行代理完成、哪些结论已被主代理验证、哪些仍待验证。
