# 第47轮：通知回执、发送完成与按钮转交的原子状态更新

开工已拉取两个上游，Core `fdc895c`、Mobile `b0cf83a` 均无新增；本轮只修改Core通知链路。

## 修复的问题

1. `provider.send()` 等待期间，手机可能先回传 `displayed/opened/failed`，原先发送完成后保存旧台账会覆盖回执状态；撤回标记也可能被旧快照冲掉。
2. 通知按钮的重复或并发回传原先每次都会调用业务处理器，包括已进入其他终态之后的迟到操作。
3. 过期清理先删队列再写台账，后一步失败时会留下半状态；发送标记与回执出队的非原子读写也存在重建旧队列项的窗口。

## 现在的行为

- 送达台账统一通过底层 `MemoryStore.transact` 读取当前值、匹配event_id并更新，支持内存与SQLite；网络调用和业务回调不占数据库事务。
- 手机的有效展示/交互回执可以证明其已收到事件，即使发送协程尚未返回，也能先推进送达再记录展示或交互状态。
- 迟到发送完成只累计真实尝试次数，不覆盖终态、终态原因或撤回状态；每次开始下一通道前重新读取台账，观察到终态/撤回后不再进入兜底发送。发送标记只更新仍存在的队列项。
- 回执推进与出队、撤回标记与出队分别在同一事务中完成；过期队列删除和对应台账推进一起提交或回滚。
- 首个按钮操作在事务里持久化认领，提交后才转交业务处理器。允许`action_submitted`回执先到、对应按钮操作后到；重复按钮和其他终态后的按钮不再触发回调。新增`action_id`仅属于本地台账，不改变V2协议；旧记录缺字段时按未认领读取。
- 旧sync快照遇到已撤回通知，不再虚报本次补发成功。

## 边界

按钮采用**至多一次转交**，不是事务outbox或“恰好一次业务执行”：认领后进程崩溃可能使回调尚未执行；回调异常也不会因重复网络回传自动重试。已有旧台账没有历史认领证据，升级后的首次按钮回传仍按新规则认领。审批处理器仍必须执行原有权限与一次性核销判断，通知本身不产生授权。

已进入通道的网络发送可能自然完成，撤回不能撤销已发送的外部副作用。并行发送仍按至少一次送达和端侧event_id去重设计；本轮不是跨进程网络发送互斥，也不把整条notify流程中的历史和队列初始化合成一个事务。
