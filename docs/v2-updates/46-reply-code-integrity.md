## 问题与行为

回复规划、自动分段、群聊长度软裁原先各自处理代码块，保护边界不一致。例如代码示例内出现 `◆` 会拆开代码，未闭合围栏内的 `[[稍后补充:示例]]` 和 `[[表情:开心]]` 会被当作真实规划意图；长度软裁还会截断代码。

现在用同一套围栏边界识别处理这几条路径：

- 支持反引号和波浪线围栏，闭合须同种字符且长度不少于开头；较短的内层围栏不结束外层代码。
- 未闭合围栏保守保护到回复末尾，模型输出不完整时也不从代码样例提取意图。
- 只解析围栏外的气泡、表情和后续补充标记，围栏内的示例标记、空行和链接原样保留；落库净文本沿用相同规则。
- 含代码围栏的气泡跳过会破坏内容的长度软裁；普通聊天仍按已有规则分段、净化和裁剪。显式气泡数量上限保留，超出部分仍合并。

这是一套面向聊天输出的保守保护规则，不是完整 Markdown 解析器。沿用对模型输出的兼容处理，围栏开头可以出现在说明文字或内联规划标记之后。代码气泡可能超过聊天长度软限制，不代表绕过传输层或输入大小限制。
